# Testing Best Practices - 測試最佳實踐

## 概述

本文件提供語言無關的測試最佳實踐指南，適用於任何程式語言和測試框架。這些原則可以幫助你撰寫高品質、可維護的測試程式碼。

## 測試類型

### 1. 單元測試 (Unit Tests)

**目的**: 測試個別函式、方法或類別的功能

**特點**:
- 快速執行
- 隔離測試
- 不依賴外部資源
- 測試單一職責

**何時使用**:
- 測試純函式和計算邏輯
- 驗證業務規則
- 測試資料轉換
- 驗證邊界條件

**範例場景**:
- 計算匯率轉換
- 驗證 email 格式
- 字串處理函式
- 數學運算

### 2. 整合測試 (Integration Tests)

**目的**: 測試多個元件之間的互動

**特點**:
- 測試元件整合
- 可能涉及資料庫
- 執行速度較慢
- 驗證資料流

**何時使用**:
- 測試 API 端點
- 驗證資料庫操作
- 測試服務間通訊
- 驗證第三方整合

**範例場景**:
- 使用者註冊流程
- 訂單處理流程
- 資料庫 CRUD 操作
- 外部 API 呼叫

### 3. 端到端測試 (End-to-End Tests)

**目的**: 測試完整的使用者流程

**特點**:
- 模擬真實使用者行為
- 測試整個系統
- 執行時間最長
- 最接近實際使用

**何時使用**:
- 關鍵業務流程
- 使用者旅程
- 跨系統功能
- 發布前驗證

**範例場景**:
- 完整的購物流程
- 使用者登入到完成任務
- 多步驟表單提交
- 支付流程

### 4. Property-Based Tests (PBT)

**目的**: 驗證程式必須滿足的通用屬性

**特點**:
- 自動生成測試案例
- 測試大量輸入組合
- 發現邊界條件
- 驗證不變性

**何時使用**:
- 數學性質驗證
- 資料轉換邏輯
- 序列化/反序列化
- 演算法正確性

**範例場景**:
- 排序演算法
- 加密/解密
- 資料格式轉換
- 業務規則驗證

詳細的 PBT 指南請參考 `property-based-testing.md`。

## 測試原則

### 1. AAA 模式 (Arrange-Act-Assert)

所有測試都應該遵循 AAA 模式：

```
// Arrange (準備)
設定測試資料和環境

// Act (執行)
執行要測試的動作

// Assert (驗證)
驗證結果是否符合預期
```

**範例概念**:
```
測試: 使用者可以加入購物車

Arrange:
- 建立測試使用者
- 建立測試商品
- 初始化購物車服務

Act:
- 呼叫 addToCart(user, product)

Assert:
- 驗證購物車包含該商品
- 驗證商品數量為 1
```

**優點**:
- 結構清晰
- 易於理解
- 容易維護
- 問題定位快速

### 2. 一個測試只驗證一件事

**原則**: 每個測試應該只有一個失敗原因

**不好的做法**:
```
測試: user_operations
- 建立使用者
- 驗證使用者存在
- 更新使用者名稱
- 驗證名稱已更新
- 刪除使用者
- 驗證使用者已刪除
```

**好的做法**:
```
測試 1: can_create_user
- 建立使用者
- 驗證使用者存在

測試 2: can_update_user
- 建立使用者
- 更新使用者名稱
- 驗證名稱已更新

測試 3: can_delete_user
- 建立使用者
- 刪除使用者
- 驗證使用者已刪除
```

**優點**:
- 失敗時容易定位問題
- 測試更專注
- 更容易維護
- 執行速度更快

### 3. 測試獨立性

**原則**: 每個測試應該獨立運行，不依賴其他測試

**不好的做法**:
```
全域變數: userId

測試 1: create_user
- 建立使用者
- 儲存 userId 到全域變數

測試 2: update_user
- 使用全域變數的 userId
- 更新使用者
```

**好的做法**:
```
測試 1: create_user
- 建立使用者
- 驗證使用者存在

測試 2: update_user
- 建立新的測試使用者
- 更新使用者
- 驗證更新成功
```

**優點**:
- 可以單獨執行任何測試
- 測試順序不影響結果
- 並行執行測試
- 更容易除錯

### 4. 使用描述性的測試名稱

**原則**: 測試名稱應該清楚描述測試內容和預期結果

**不好的命名**:
```
test1()
test_user()
test_validation()
testMethod()
```

**好的命名**:
```
can_create_user_with_valid_email()
prevents_duplicate_email_registration()
validates_password_minimum_length()
calculates_discount_correctly_for_premium_users()
```

**命名模式**:
- `should_[expected_behavior]_when_[condition]`
- `can_[action]_with_[condition]`
- `[action]_[expected_result]_[condition]`
- `validates_[rule]_for_[scenario]`

**優點**:
- 測試即文件
- 失敗時立即知道問題
- 容易理解測試意圖
- 提高程式碼可讀性

### 5. 測試邊界條件

**原則**: 測試邊界值和特殊情況

**應該測試的邊界**:
- 最小值和最大值
- 空值和 null
- 零和負數
- 空字串和空陣列
- 超出範圍的值

**範例**:
```
測試金額驗證:
- 最小有效值: 1
- 最大有效值: 1000000
- 邊界下限: 0 (應該失敗)
- 邊界上限: 1000001 (應該失敗)
- 負數: -100 (應該失敗)
- 空值: null (應該失敗)
```

**優點**:
- 發現邊界錯誤
- 提高程式碼健壯性
- 避免生產環境問題
- 完整的測試覆蓋

### 6. 避免測試實作細節

**原則**: 測試行為而非實作

**不好的做法**:
```
測試: 驗證內部變數狀態
- 檢查私有變數的值
- 驗證內部方法被呼叫
- 測試實作邏輯
```

**好的做法**:
```
測試: 驗證公開行為
- 測試公開 API
- 驗證輸出結果
- 測試副作用
```

**優點**:
- 重構時測試不會失敗
- 測試更穩定
- 關注使用者體驗
- 更容易維護

## 測試覆蓋率

### 覆蓋率目標

**建議的覆蓋率標準**:
- **整體覆蓋率**: 70-80%
- **核心業務邏輯**: 90%+
- **服務層**: 85%+
- **工具函式**: 90%+
- **控制器/路由**: 60-70%
- **UI 元件**: 50-60%

### 覆蓋率不是唯一指標

**重要提醒**:
- 100% 覆蓋率不代表沒有 bug
- 測試品質比數量重要
- 關注關鍵路徑
- 邊界條件比覆蓋率重要

### 必須測試的項目

**1. 核心業務邏輯**
- 計算和演算法
- 業務規則驗證
- 資料轉換
- 狀態管理

**2. 資料驗證**
- 輸入驗證
- 格式檢查
- 業務規則
- 權限檢查

**3. 錯誤處理**
- 例外處理
- 錯誤訊息
- 回滾機制
- 失敗恢復

**4. 安全性**
- 認證邏輯
- 授權檢查
- 資料加密
- 輸入清理

## Mock 使用指南

### 何時使用 Mock

**✅ 應該使用 Mock**:
- 外部 API 呼叫
- 第三方服務
- 檔案系統操作
- 網路請求
- 郵件發送
- 推播通知
- 時間相關功能
- 隨機數生成

**❌ 不應該使用 Mock**:
- 核心業務邏輯
- 簡單的計算
- 資料轉換
- 純函式
- Property-Based Tests
- 資料庫操作（使用測試資料庫）

### Mock 最佳實踐

**1. 最小化 Mock 使用**
- 只 mock 必要的部分
- 優先使用真實物件
- 考慮使用測試替身

**2. 驗證互動**
- 驗證方法被呼叫
- 檢查參數正確性
- 確認呼叫次數

**3. 避免過度 Mock**
- 不要 mock 所有依賴
- 保持測試真實性
- 考慮整合測試

## 測試資料管理

### 測試資料原則

**1. 使用有意義的測試資料**
```
❌ 不好:
user = { name: "test", email: "test@test.com" }

✅ 好:
user = { name: "John Doe", email: "john.doe@example.com" }
```

**2. 避免魔術數字**
```
❌ 不好:
assert amount == 100

✅ 好:
const MINIMUM_TRANSFER_AMOUNT = 100
assert amount == MINIMUM_TRANSFER_AMOUNT
```

**3. 使用 Factory/Builder 模式**
- 集中管理測試資料
- 提供預設值
- 支援客製化
- 提高可維護性

### 測試資料庫

**策略選擇**:

**1. 記憶體資料庫**
- 優點: 快速、隔離
- 缺點: 可能與生產環境不同
- 適用: 單元測試

**2. 測試資料庫**
- 優點: 與生產環境相同
- 缺點: 較慢、需要清理
- 適用: 整合測試

**3. 交易回滾**
- 優點: 自動清理
- 缺點: 可能隱藏問題
- 適用: 大部分測試

## 測試組織

### 測試檔案結構

**建議的目錄結構**:
```
tests/
├── unit/                    # 單元測試
│   ├── services/
│   ├── models/
│   ├── utils/
│   └── properties/         # Property-Based Tests
├── integration/            # 整合測試
│   ├── api/
│   ├── database/
│   └── services/
├── e2e/                    # 端到端測試
│   ├── user-flows/
│   └── critical-paths/
├── fixtures/               # 測試資料
├── helpers/                # 測試輔助函式
└── setup/                  # 測試設定
```

### 測試檔案命名

**命名規範**:
- 單元測試: `{ClassName}.test.{ext}` 或 `{ClassName}.spec.{ext}`
- 整合測試: `{Feature}.integration.test.{ext}`
- 端到端測試: `{UserFlow}.e2e.test.{ext}`
- Property-Based Tests: `{Feature}.properties.test.{ext}`

**範例**:
```
UserService.test.js
PaymentService.spec.ts
checkout.integration.test.py
user-registration.e2e.test.js
transfer.properties.test.php
```

## 測試執行

### 測試執行策略

**1. 本地開發**
```bash
# 快速反饋循環
- 執行相關測試
- 使用 watch 模式
- 跳過慢速測試
```

**2. 提交前**
```bash
# 完整測試套件
- 執行所有單元測試
- 執行相關整合測試
- 檢查測試覆蓋率
```

**3. CI/CD**
```bash
# 全面驗證
- 執行所有測試
- 增加 PBT 案例數
- 產生覆蓋率報告
- 執行端到端測試
```

### 測試執行時間

**目標**:
- 單元測試: < 1 秒
- 整合測試: < 10 秒
- 端到端測試: < 1 分鐘
- 完整測試套件: < 10 分鐘

**優化策略**:
- 並行執行測試
- 使用測試快取
- 優化測試設定
- 移除重複測試

## 測試維護

### 保持測試更新

**1. 與程式碼同步**
- 修改程式碼時更新測試
- 重構時檢查測試
- 新功能必須有測試

**2. 定期審查測試**
- 移除過時的測試
- 更新測試資料
- 改進測試品質

**3. 測試程式碼品質**
- 遵循相同的程式碼標準
- 避免重複程式碼
- 使用輔助函式
- 保持測試簡潔

### 處理失敗的測試

**1. 立即修復**
- 不要忽略失敗的測試
- 不要註解掉測試
- 找出根本原因

**2. 分析失敗原因**
- 測試錯誤
- 程式碼錯誤
- 環境問題
- 測試資料問題

**3. 改進測試**
- 增加錯誤訊息
- 改善測試穩定性
- 更新測試文件

## 測試文件化

### 測試註解

**應該包含的資訊**:
- 測試目的
- 測試場景
- 預期結果
- 相關需求編號

**範例**:
```
/**
 * @test
 * @validates Requirements 2.1
 * 
 * 測試: 使用者可以使用有效的 email 註冊
 * 
 * 場景:
 * - 提供有效的 email 和密碼
 * - 系統建立新使用者
 * - 發送驗證郵件
 * 
 * 預期:
 * - 使用者成功建立
 * - 驗證郵件已發送
 * - 使用者狀態為 pending
 */
```

### 測試報告

**應該包含的內容**:
- 測試摘要（通過/失敗/跳過）
- 測試覆蓋率
- 失敗測試詳情
- 執行時間
- 測試環境資訊

## 常見陷阱

### 1. 脆弱的測試

**問題**: 測試經常因為無關的變更而失敗

**解決方案**:
- 測試行為而非實作
- 避免測試內部狀態
- 使用穩定的選擇器
- 減少對時間的依賴

### 2. 慢速測試

**問題**: 測試執行時間過長

**解決方案**:
- 使用記憶體資料庫
- 並行執行測試
- 減少不必要的設定
- 優化測試資料

### 3. 不穩定的測試

**問題**: 測試結果不一致

**解決方案**:
- 避免依賴外部服務
- 控制隨機性
- 處理非同步操作
- 清理測試資料

### 4. 過度測試

**問題**: 測試過多的細節

**解決方案**:
- 關注公開 API
- 測試使用者行為
- 避免測試框架功能
- 合併相似的測試

## 測試驅動開發 (TDD)

### TDD 循環

**Red-Green-Refactor**:

1. **Red (紅燈)**
   - 撰寫失敗的測試
   - 定義預期行為

2. **Green (綠燈)**
   - 撰寫最少的程式碼讓測試通過
   - 不考慮優化

3. **Refactor (重構)**
   - 改進程式碼品質
   - 保持測試通過

### TDD 優點

- 更好的設計
- 更高的測試覆蓋率
- 更少的 bug
- 更容易重構
- 測試即文件

### 何時使用 TDD

**適合 TDD**:
- 新功能開發
- 複雜的業務邏輯
- 演算法實作
- Bug 修復

**不適合 TDD**:
- 探索性開發
- 原型設計
- UI 設計
- 簡單的 CRUD

## 總結

**測試的核心原則**:
1. 測試應該快速且可靠
2. 測試應該獨立且可重複
3. 測試應該清楚且易於理解
4. 測試應該測試行為而非實作
5. 測試應該與程式碼一起維護

**記住**:
- 測試是投資，不是成本
- 好的測試提高開發速度
- 測試讓重構更安全
- 測試是最好的文件
